# Executable local monitor/failover drill proposal

Read-only design; no code, deployment, package build or test run performed. The smallest independent drill is an Ethereum-only disposable fixture with the real portal and canonical Inbox/Outbox, using the existing controlled-root publisher. It needs no Aztec node, application proof, epoch advancement or network prover. This establishes monitor command behavior on genuine deployed portal state; it does not qualify real-rollup activation.

## Reuse and one missing fixture method

- `scripts/test-deployment-runtime-anvil.mjs` already provides pinned Anvil startup, ephemeral random operator funding, real `BillboardPortal` deployment, source-bound runtime verification and owned cleanup. Reuse its sequence, not its code-mutation phase.
- `scripts/test-w03-ethereum-anvil.mjs` lines 43–55 deploys `RootPublisher`, computes the exact Ready leaf with `encodeReadyCommitment` / `sha256Field`, publishes it through the controlled publisher and calls the actual portal `activate`. The publisher uses the canonical Inbox and Outbox contracts, including actual Outbox consumption verification.
- Important incompatibility: `RootPublisher` in `billboard/portal/test/PortalV1.t.sol` exposes `getInbox` and `getOutbox` but **no `getVersion`**. The production monitor calls all three and must not be loosened. Add a narrow test-only subclass `MonitorRootPublisher is RootPublisher` in a new `billboard/portal/test/MonitorRootPublisher.sol`, with a constructor-set immutable version and `getVersion()` getter. Compile the new fixture using the existing regression Foundry profile before the drill. Preserve the real portal artifact and runtime metadata unchanged.
- `packageOperator({nodePath,destination})` from `scripts/package-operator.mjs` produces the actual package and manifest. Prepare it once outside the live fixture; accept an explicit existing package path, verify its manifest/source identity, and invoke its `scripts/operator-launch.sh monitor <config>`. Do not construct an imitation runtime or modify packaged sources.

## Proposed implementation files and phases

Add `scripts/test-o01-monitor-failover-anvil.mjs` and the test-only subclass above. Optionally isolate the small HTTP forwarding helper into `scripts/o01-monitor-drill-transport.mjs` if needed for offline rejection/cancellation tests. No changes to the running browser harness or production monitor are required.

1. Start a fresh loopback Anvil at normal wall time using the existing version pin and cleanup pattern. Deploy the publisher and unmodified real portal. Verify runtime and all immutable identities. Before activation, an optional actual packaged command must return `PORTAL_INACTIVE`; this is useful but not needed for the three-step failover gate.
2. Publish the correctly scoped Ready root and activate via the portal's normal method. Make one small actual ETH deposit with a nonzero field secret hash. This gives a nonzero liability/balance assertion, stronger than observing an empty escrow. These are fixture setup transactions, not monitor actions. Preserve canonical setup receipts and confirm `totalDeposited == portal balance == deposit amount`.
3. Stop making transactions and leave normal Anvil automining idle. Read the latest canonical block and assert it is within the production monitor's unchanged wall-time range. Create the strict public config from real addresses/version/chain. `nodeUrl` is required by the config schema but unused by this Ethereum-only command; use a clearly local endpoint and record that no Aztec service is running.
4. Start two separate loopback forwarding transports to this same Anvil and one loopback failure endpoint. Forward only the monitor's read methods (`eth_chainId`, `eth_getBlockByNumber`, `eth_call`, `eth_getCode`, `eth_getBalance`). Bound JSON and response sizes; reject batches/mutations not needed by the actual command. Track controllers/sockets for cancellation. Failure endpoint returns HTTP 503 immediately so the drill fits a short budget; existing cancellation tests already cover hanging HTTP disposal.
5. Execute three actual packaged commands with a shared 15-second observation deadline: primary config -> `ESCROW_BALANCED` / exit 0; same identity with failure URL -> `OBSERVATION_UNAVAILABLE` / exit 2; same identity with alternate URL -> `ESCROW_BALANCED` / exit 0. Require identical canonical block number and expected active/liability/balance values for both successful outputs, since no fixture transactions occur during observation. Independently call `readEscrowSnapshot` and check the same accounting and identity. Verify the Anvil block and operator nonce did not advance during the monitor phase.
6. Close child processes, all HTTP connections and request controllers, destroy the provider and terminate owned Anvil. Remove only owned configs/temp directories; leave an explicitly supplied package intact. Emit fixed parsed classifications, command exit codes, canonical public setup hashes, package/source hashes, accounting values, method counts, elapsed time and cleanup booleans. Never retain raw subprocess errors, RPC bodies or fixture private keys.

## Bounds and acceptance

Use the existing Ethereum-only fixture's 60-second watchdog as an initial total bound (package/compile preparation excluded); the three command observations have a separate 15-second bound. Run serially after the active browser job and under the existing resource discipline. These are proposed budgets, not measured performance claims. No proof job or network epoch is part of this work.

Keep actual monitor freshness checks (+30 seconds / -180 seconds) untouched. Normal Anvil startup and a short, unwarped fixture remove the accelerated-chain problem described in preparation-012. If the normal-clock assertion fails, record failure; do not rewrite timestamps or fake `Date.now`. The earlier accelerated fixture can still demonstrate stale classification and direct accounting separately, but is not needed here.

This closes the missing genuine packaged healthy -> unavailable -> healthy command drill with actual portal balances and alternate local transport. It does **not** establish independence of production RPC providers, real Aztec Ready proofs, mainnet deployment suitability, or the separate censor transfer/policy-update drill.
