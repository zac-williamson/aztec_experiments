# Bounded operator batch registration and restart design

Design only. No implementation, chain transaction, build or runtime test was performed. This is the missing operator integration between the current durable issuer and the existing sponsor contract; it does not add a platform or complete W01.

## Existing boundary

The issuer persists fixed scope/policy, next batch ID, per-window liability, batches, slots and paths. Seal makes roots immutable; currently there is no public list of pending batches, registration journal, canonical-state reconciliation or administration HTTP route. Retention deliberately stops at64 batches/windows. The issuer returns pending/usable:false. The provider independently checks actual registered state before returning a coupon.

The sponsor registers `(batch_id,root,window,ticket_count)` through the current admin's ordinary public call. `register_batch` checks an unused global ID, immutable config, unexpired window and available public `reserved_by_window` budget, then initializes batch and reserves `count * max_fee_per_ticket` atomically. Holes count. There is no reset/reclaim/root replacement. Registration of future windows is allowed by the contract; current issuer allocation is current-window-only. Admin rotation changes future authority, not existing roots/liabilities.

Source: billboard/sponsor_contract/src/main.nr register_batch/get_admin/get_batch/get_reserved; billboard/sponsor_common/src/lib.nr reserve_batch/window_bounds; sponsor-service/issuer.mjs schema, reserve, seal and bounded restart validation.

## Smallest local worker and journal

One operator process, one bounded local issuer database, one active registration job. Keep operator wallet keys outside the issuer database and HTTP process. The existing fixed HTTP API must not gain signing, seal, funding or admin endpoints.

Add a separate registration table in the same database, keyed by immutable batch ID. Store the exact intent tuple and scope/config/artifact hashes, revision, state, attempt number, prepared transaction bytes/hash/SHA256, bounded timestamps, latest sanitized receipt observation and canonical block hash/number. Transaction bytes belong in the private durable database, not logs or API responses. No owner/blind is needed by this worker. Actual proven registration transaction bytes contain the operator's transaction/proof and public registration data; never persist a PXE witness or dump a wallet object.

States: `sealed -> preparing -> prepared -> submission-uncertain -> pending -> included -> confirmed`, with explicit `expired`, `reverted`, `state-conflict` and `blocked-reconciliation` dispositions. An attempt history is append-only; it must not overwrite uncertain transactions. A database compare-and-swap revision and process lock prevent two workers from preparing/sending the same job. Before send, atomically persist submission-uncertain; a crash before/after the network call is therefore conservatively ambiguous. Every mutation uses a short database transaction; never hold a write lock while proving, signing or doing RPC work.

Required issuer-side interfaces (not currently implemented):

- `listBatches({cursor,limit,status,window})`: bounded operator-only projection of public batch tuples, counts and sealing state; no raw retrieval tokens or slot commitment lists in operational logs.
- `sealAndQueue({batchId,expectedRevision})`: use current freeze/hash/commit pattern, then atomically record the sealed root and a registration intent. Interrupted sealing resumes; exact root cannot reopen or change. If queueing is a separate call, it must compare the actual sealed tuple and insert idempotently in a transaction.
- `claimRegistrationJob` / `savePreparedAttempt` / `recordRegistrationObservation`: strict state/revision CAS, bounded bytes, exact intent and attempt hash; no generic database edit API.
- `reconcileAdmission({canonicalObservation,expectedRevision})`: persist a checked onchain scope/admin/budget/history fence and block admission when that fence is invalid, missing or rollback is suspected. Do not accept arbitrary unsigned caller-supplied 'registered' flags from HTTP.
- A retention/archival operation must preserve the ID high-water mark, liability/history and external recovery anchor. Until qualified, reaching64 retained batches stays an explicit operational stop. Deleting rows to resume issuance is not an acceptable workaround.

Current core startup expects exactly two meta entries and its existing schema. This design requires an explicit schema-version migration and validation of new journal tables; appending metadata ad hoc would break or bypass its invariants. Preserve existing batch-ID history and old records. Migration concerns the new local service state, not legacy board deployments.

## Registration execution

1. Before collecting/submitting batches, verify node/wallet expected chain/version, sponsor original/current class and instance address against the pinned local artifact, immutable board/config and live admin. Read actual FeeJuice balance and public reserved budget. Operator control must be explicit; no author wallet or author-funded fallback.
2. Seal a common batch by configured capacity/dwell policy with enough time left for proof/inclusion. The policy must state its minimum sharing target and expiry behavior; do not silently use one-client roots while claiming a large anonymity set. If the target cannot be met before expiry, stop/expire that batch rather than inventing a privacy guarantee.
3. Build exactly `sponsor.methods.register_batch(batchId,root,window,count)` from persisted sealed intent; use the actual operator wallet request/fee/prove path already exercised by scripts/prove-application-action.mjs and scripts/w01-sponsor-flow.mjs. This is an operator transaction with ordinary operator fees, not a user sponsor coupon. No unrelated administration call may be bundled.
4. Obtain the genuine `Tx`; check scope, gas cap, nonempty proof, expected operator payer and its exact public call using `Tx.getPublicCallRequestsWithCalldata()`. Pinned PublicCallRequestWithCalldata exposes request.contractAddress/msgSender, functionSelector and args. Compare selector and ABI-encoded arguments to the immutable registration intent; permit only the precisely documented account/fee scaffolding, not arbitrary extra calls. Persist `tx.toBuffer()` plus full SHA256, exact byte count, `tx.getTxHash()`, request intent and source identity before calling node.sendTx. Use a declared bounded transaction-byte cap and qualify it against an actual registration fixture.
5. Reopening deserializes with actual `Tx.fromBuffer`, checks byte roundtrip and SHA256, recomputes `await Tx.computeTxHash(tx)` against the stored hash, and repeats exact public-call/intent checks. `getTxHash()` alone reads the serialized cached value and is not independent integrity verification. Preserve full proof bytes: do not use withoutProof().
6. Submit once and reconcile the exact hash. Unknown outcome retains submission-uncertain and stops automatic replacement. Known pending/proposed is monitored. Canonical inclusion requires exact tx hash, SUCCESS, block number/hash matching the node's canonical BlockResponse and actual get_batch tuple matching the sealed intent. Confirmation depth/finality policy is explicit and rechecked; actual chain state and receipt observations remain provider-backed until their stated protocol finality. Never fabricate a proof/finality receipt.

## Restart, replacement and rollback

Reuse the application's proven distinction between pending/proposed, successful inclusion, dropped, unknown and execution failure. See engine submitOnceWithReconciliation/classifyDroppedTransaction/requireSuccessfulReceipt. After checking node.isValidTx, reread the exact receipt because inclusion can race validation. Unknown/mixed dropped reasons do not authorize a new transaction. An existing-nullifier error alone does not prove this batch registered.

On restart, reconcile every nonterminal exact transaction before taking another job. If get_batch matches but the worker lacks the canonical registration receipt, record `observed-existing` separately; it establishes current tuple availability, not that this worker's transaction succeeded or incurred its alleged fee. Conflicting root/window/count for an ID is a hard reconciliation stop. Do not choose another root or ID for the same clients: their leaf already commits to batch ID/window/index.

After a conclusively failed/invalid old attempt, an unregistered still-unexpired batch may be re-proved with refreshed operator state, bounded new gas and the SAME sealed tuple/ID. Preserve the old attempt. A registered ID is never registered twice. A reorg removing its registration does not reopen its root or recycle its ID; invalidate the confirmation observation and reconcile exact prior attempt, canonical state and validity before any bounded recovery action. Ambiguous old attempts remain blocked. Expired batches become terminal; never shift their coupons into a later window or decrement historical liability to manufacture budget.

**Whole-database rollback has a concrete missing prerequisite.** The current contract exposes get_batch(id) and get_reserved(window), but no enumerable registered IDs/high-water mark or registration event. Checking known IDs or a single aggregate cannot prove a restored database did not lose later IDs, particularly across windows/admin changes. A safe first implementation must detect a mismatched external backup/journal checkpoint and halt new allocation. Full recovery needs an independently retained append-only high-water/registration history anchored to canonical chain observations, or a later authenticated registration-event/enumeration interface. Do not claim a self-hash stored in the same rolled-back database solves this. If the recovery anchor is unavailable, stop; redeployment/ID reset is not automatic recovery.

## Budget, expiry, replenishment and observations

The core's local reserved amount includes open/sealing/sealed batches, including holes; public reserved tracks registered batches. They are distinct. At a coherent canonical observation, separate exact known registered local liabilities from unregistered local liabilities and any unexplained external registered liability. Require onchain reserved plus local unregistered liability to fit the immutable window budget. If observations disagree or another admin/worker registered unknown batches, halt admission/reconcile. The final contract registration check is authoritative, but relying on its rejection alone would strand already issued reservations. Reads must be tied to a supported common canonical view or checked for tip changes and retried boundedly; do not silently equate independent changing latest reads to one snapshot.

Window end is inclusive (`window * duration + duration - 1`). Reject expired registration and insufficient operational time margin before beginning expensive proof work. Expiry during proof/submission can still occur; record the actual failure without changing the contract bound. Exhausted budget, local retention, unknown admin, insufficient sponsor balance or uncertain registration are explicit stop/outage states. Never fall back to charging the author.

Track aggregate counts of open/sealing/registered/expired/uncertain batches and slots, reserved liabilities, actual sponsor balance, replenishment pending amounts, registration fees, failure classes and confirmation latency. No owner, blind, token, per-client request ID, transport IP or commitment metric labels. Common root/registration timing and the operator's shared payer remain visible; this architecture is not network anonymity or Sybil resistance.

Replenishment uses the already exercised real L1 FeeJuicePortal deposit and operator FeeJuice.claim(to=sponsor,...) path in scripts/w01-shared-funding.mjs. It needs its own durable signed-L1-transaction and exact L2-claim journal, with the claim secret encrypted before L1 submission, canonical receipt/message reconciliation and actual sponsor balance delta. No invented L2 user token transfer. Funding amounts, thresholds and authority are operator inputs; the service cannot grant itself production spending authority.

## Smallest discriminating qualification

Before production use: real SQLite crash-boundary tests at seal/prepare/send/receipt persistence; two-process CAS/no double preparation; exact serialized Tx hash/calldata roundtrip; uncertain send with eventual exact inclusion; inclusion-during-revalidation; public revert without false success; wrong admin/class/config; window expiry and exhausted public budget; conflicting registered tuple; missing/rolled-back external recovery checkpoint stopping allocation. Then one ordinary local genuine registration transaction through this worker with shared issuer/provider retrieval and no author funding. Existing controlled local settlement is sufficient for that application test boundary; it must not be relabeled protocol finality. No network prover or long-running proving fleet is part of this design.

## Integration correction: inclusion and finality have different jobs

The initial journal draft held its only submission slot until finality. That would prevent ordinary new batches while an already successful registration awaited protocol finality, exceeding the client delivery budget. Root changed the integration policy: a checked canonical successful inclusion releases the submission slot, while the included record remains durably monitored until finalized. Pending/uncertain work retains the slot. An observed rollback fences new preparation/submission globally, and rollback-to-pending must reacquire the slot before recovery. This is application inclusion/recovery logic, not network-epoch proving or a finality claim. A dedicated two-batch/restart/rollback control verifies this policy. The historical15-test handoff used the earlier conservative policy; the new source and16-test evidence supersede that claim-state detail.
