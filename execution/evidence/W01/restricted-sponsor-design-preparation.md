# W01 restricted shared sponsor — design preparation

2026-09-14. Read-only preparation during A02 verification; no source/dependency changes, installation, local chain, proof, transaction or benchmark. This is a feasible construction to test using pinned5.2 primitives, not a compiled or accepted W01 implementation. X03 target-network clearance remains separate.

## Proposed direction and important limits

Qualify a **sponsor-owned private transaction entrypoint**, with finite privately committed coupon batches, which performs exactly one approved delegated board operation. It consumes its coupon in non-revertible setup, checks actual transaction gas settings and expiry, elects the shared payer, ends setup, then calls the approved board method. This is stronger than a normal fee hook that merely checks a service-signed quote while an arbitrary account appends other calls.

This needs a coordinated fresh board ABI: a delegated private operation accepting an explicit owner and authenticating that owner's exact action. Current msg_sender-based board operations cannot simply be called by the sponsor without changing who is treated as owner. The alternative is an integrated board-sponsored root operation that uses the same controls and internal posting logic; it changes which shared contract holds FeeJuice. Neither interface has been implemented or selected. Before C01/C02/C03 implementation freezes their interfaces, record the chosen delegated/root path, preserve authenticated owner/note binding, private chain semantics and independent post IDs, and add corresponding negative tests. No legacy ABI compatibility is required.

The [official current fee guide](https://docs.aztec.network/developers/docs/aztec-js/how_to_pay_fees), rechecked today, says the built-in unconditional SponsoredFPC is unavailable on mainnet and the reference Private/PublicFeePaymentMethod classes are deprecated and unsupported on mainnet alpha. It also documents custom third-party FPCs. Do not interpret that as approval of this proposed contract or use the unsupported reference token method as a shortcut. The unconditional contract remains only a disposable local mechanism control.

## Why application binding needs a constrained call path

Pinned `PrivateContext.maybe_msg_sender()` documents that only the first **private** function call has no sender. AppPayload explicitly rejects hide_msg_sender for private calls. Therefore a sponsor root can assert `maybe_msg_sender().is_none()`; a malicious outer account cannot prepend/appended sibling calls around that private root by disguising a private caller as absent. A root entrypoint owns its call sequence rather than inspecting an unavailable global transaction-call-list API.

The ordinary SDK SponsoredFeePaymentMethod only adds one private sponsorship call; FeePaymentMethod receives no complete app payload to constrain. A signed target/hash argument alone does not prove that the signed action occurred or that arbitrary other calls did not occur. Likewise forwarding a checked AppPayload through an arbitrary user account is insufficient: malicious account code could ignore that payload and execute different calls. The installed standard account implementation does validate/execute its payload, but that does not authenticate arbitrary account code.

Private `get_contract_instance(address)` authenticates the address preimage. It is not a generic proof of the **currently executing upgraded class**. The current-class getter inspected is AVM/public. Do not assume an original class/address check solves malicious or upgraded account forwarding.

The proposed root therefore calls one fixed, reviewed board address and delegated selector directly; no caller-supplied arbitrary call array, arbitrary account entrypoint, callback, or user teardown. A delegated board method validates its private owner explicitly using the pinned `assert_current_call_valid_authwit` or a precisely defined `assert_inner_hash_valid_authwit` message, plus the existing note-owner/slot/contract membership conditions. The helper uses a **static** private account verification call, checks its return selector and emits replay protection; it does not allow an account callback to change state. A malicious account may still spend bounded computation, so gas caps remain mandatory. The board implementation itself must not expose an arbitrary forwarding route from that allowed method; contract upgrade policy must also remain within the reviewed code assumptions.

## On-chain finite budget without forbidden setup counters

Prefer an admin-approved, one-time `PublicImmutable<EpochPolicy>` for each batch, optionally in a Map keyed by epoch. Initialize it in a separate ordinary public administrative transaction, never by enqueuing a custom public call inside sponsored setup. Private reads of initialized PublicImmutable are supported and authenticated. Batch publication/funding is public operator activity, common to the whole batch.

Concrete candidate typed policy fields (schema1):

- `schemaVersion:u32`, `epochId:Field`, `couponRoot:Field`, `ticketCount:u32` with `0<ticketCount<=2^D` for compile-time Merkle heightD.
- `boardAddress:AztecAddress`, `operationSelector:FunctionSelector` or a fixed small operation enum mapped internally to selectors; `policyVersion:Field` for the approved board/policy configuration.
- `validFrom:u64`, `validUntil:u64`, with a bounded shared batch window.
- Caps matching GasSettings: total `daGas/l2Gas:u32`, teardown `daGas/l2Gas:u32`, max fee-per-DA/L2 and priority-per-DA/L2 `u128`, plus `maxFeePerTicket:u128`.
- An explicit public approval amount/budget satisfying `ticketCount * maxFeePerTicket <= epochBudget` using checked arithmetic. This is a worst-case reserved authorization budget, not a mutable actual-spend balance or a promise of gas refunds.

Candidate leaf: Poseidon2 over a fixed schema/domain field followed by `(epochId,index,ownerAddress,leafBlind)`, with a distinct domain for leaves versus policy/action hashes. Scope additionally binds the actual sponsor address, context chain_id and protocol version either in the leaf transcript or immutable policy hash. Freeze exact domain constants/encoding and cross-language vectors before implementation. Range-check index and every raw packed typed boundary; do not rely on truncating casts. Merkle membership uses the actual pinned `MembershipWitness<D>`/`check_membership`; explicitly require `index<ticketCount` and `index<2^D`.

For replay, use `Map<EpochIndex, Owned<SingleUseClaim>>` scoped to the **leaf-bound owner**. SingleUseClaim derives its nullifier from the owner's validated app-siloed nullifier-hiding key, storage slot and owner address, then the protocol silos it by sponsor contract. Exactly one owner is committed at each valid root position, so changing owners cannot obtain extra claims for that position without breaking membership. Domain/Map layout must separate this claim from other sponsor state. Claim before `end_setup`; retries, concurrent spends and public application reverts must not restore this coupon. Private failure before submission is different and should leave no accepted spend.

Thus at most `ticketCount` accepted coupon spends, each costing at most the actual checked cap, imply an enforced epoch liability bound even if callers bypass the issuer service. For an actual per-period rate/spend ceiling, the public batch-registration method must enforce one immutable root per canonical period index, fixed period boundaries, non-overlapping windows and protocol-configured maximum ticket/budget caps; callers must not invent multiple epoch IDs for the same period. Batch issuance is an administrative transaction, so these aggregate registration checks can use ordinary public mutable state outside sponsored setup. An unrestricted admin API that creates unlimited overlapping batches would enforce only a per-batch limit, not the required rate policy. This avoids a contended mutable public spending counter during setup. It does **not** provide fairness/Sybil resistance or stop an issuer distributing all coupons to one requester. Immutable batches also cannot be instantly revoked; use short common expiry windows and bounded outstanding commitments. Mutable emergency policy would require separately verified DelayedPublicMutable expiry semantics, not an assumed instant private read.

## Issuance privacy and nullifier linkage

Do not publish `H(issuerKnownNonce)` as a coupon nullifier: the issuer could map every issued request to a later public consumption. Do not log owner/coupon/spend preimages or require a reusable public author identifier for ordinary issuance.

Practical candidate: the user locally forms an opaque leaf commitment from its private owner address and fresh high-entropy leafBlind; the issuer places that commitment at a fixed index in a batch and returns the inclusion witness. It need not learn the owner or blinding value. The issuer knows the leaf/index and batch, but cannot calculate SingleUseClaim's spend nullifier without the owner's NHK. SingleUseClaim also avoids inventing a new nullifier-hiding primitive. This design needs an actual experiment showing the issued leaf/index does not appear publicly and that nullifiers differ across tickets/accounts without revealing reusable owner tags.

A user-secret commitment with a custom domain-separated secret-derived spend nullifier is another possible construction, but must constrain membership, index, secret opening and uniqueness carefully; do not use push_nullifier_unsafe casually when a supported owned claim suffices. Cryptographic blind-signature issuance could reduce issuer correlation further, but no compatible blind-signature implementation was inspected here and it is not assumed available.

Opaque batch issuance is not network anonymity: issuer/RPC observations, IP/authentication, batch membership, timing, uncommon operation/gas/expiry values and funding can correlate requests. Batch publication should group many users with common expiry/cap profiles; measure the actual anonymity set. The owner-authwit nullifier also needs review: that helper hashes owner plus inner message, rather than NHK-hiding it. Include a fresh user-held nonce in the delegated action authorization and avoid disclosing its complete private preimage to the issuer; analyze **all** transaction nullifiers/effects, not only the sponsor claim.

## Actual gas, expiry and setup constraints

`context.gas_settings()` returns the transaction's actual declared settings. Compare every dimension to approved caps, including priority price and teardown; require priority<=max price and teardown<=total. The SDK's `GasSettings.getFeeLimit()` is `totalDA * maxFeeDA + totalL2 * maxFeeL2`. Teardown is reserved within total gas, so do not add it a second time. Constrain the arithmetic and final total into the approved u128 fee budget; field arithmetic without integer bounds is not an overflow check. Actual charging is still measured against TxEffect/receipt and payer balance writes.

Call `set_expiration_timestamp(validUntil)` before phase end; it restricts the publicly visible protocol inclusion deadline. Check a valid anchor timestamp against validFrom, if a not-before window is needed; checking anchor time alone is not a replacement for the protocol inclusion expiry. Other functions may lower the deadline. Shared/coarsened deadlines reduce uniqueness but cannot exceed safety limits. The protocol's maximum transaction lifetime and unavailable/current network setup policy remain hard constraints.

Pinned default public setup allowlist contains AuthRegistry authorization methods and FeeJuice `_increase_public_balance`; it does not authorize a new sponsor public counter or token transfer. The proposed coupon membership, private claim, immutable read and fee election are private setup work; the board call comes **after** `end_setup`. Do not validate feasibility using local-network's extended token allowlist. One-time sponsor config/funding must already be available at the chosen anchor. FeeJuice replenishment uses the supported protocol funding route; do not assume arbitrary withdrawal/refund of unused FeeJuice is available.

## SDK/client integration requirement

Root's `client-fee-integration-preparation.json` shows current post/dummy/claim/withdraw use the default from-only fee route, and the pre-prove hook precedes construction of finalGasSettings. A fee payload must exist before simulation; a late hook cannot silently replace the payer or authorize a stale gas estimate.

The installed DefaultEntrypoint can build a TxExecutionRequest for exactly one private root call, retaining authWitnesses/capsules/extraHashedArgs and explicit tx gas context. That is a concrete starting API for this restricted root, rather than assuming a FeePaymentMethod appended inside an ordinary account transaction is equivalent. The custom browser wallet needs an explicit integration path and SDK exports/tests; simply attaching SponsoredFeePaymentMethod will not satisfy the root-only constraint.

Use a two-stage client construction: prepare the exact delegated action/coupon payload, estimate it without claiming fee acceptance, derive capped final settings, then rebuild/freeze any authorization transcript tied to those final settings and prove that exact request. Alternatively a coupon can authorize fixed bounds rather than exact gas values, with the circuit checking the final context lies within them. Never mutate app arguments, payer, expiry or fee settings after authorization without revalidation. Inspect actual proven Tx feePayer, not only a JS configuration field. Unsupported, empty or depleted sponsorship fails explicitly; never auto-fund or fall back to the author account.

## Smallest discriminating experiment when W01 activates

First implement a tiny local Noir fixture, not the production board: sponsor root plus delegated counter operation using real owner authwit and a batch of two leaves at height1. Compile with exact5.2/beta25. Test actual constrained methods for valid membership/owner, wrong leaf/index/root/scope/owner, range boundaries, exact cap and cap+1 for every gas field, invalid expiry and nested-root caller. Pure tests establish constraints only, not fee charging or protocol validation.

Then use a bounded disposable local network with **default-equivalent setup allowlist**, fresh accounts A/B and a shared pre-funded sponsor. Run A/B/A coupon spends, replay/concurrent use, invalid app substitution and malicious account-forwarding controls, public application revert, low sponsor balance, and expired inclusion. Capture real private proof/Tx feePayer, sponsor/author balance effects, setup coupon persistence on public revert, receipt execution/finality and all public nullifiers. The malicious outer account must fail root-only admission; an arbitrary account entrypoint must never become the sponsor's unchecked execution router. Include the unconditional sponsor/default author payer only as explicit negative controls. Separately exercise real replenishment and observability; genesis funding is not funding privacy evidence. A synthetic/fake verifier local network cannot establish L1 real-proof acceptance.

For the first experiment keep infrastructure bounded and use Node24.21 from A02, not the old24.15 command in the historical preparation. No experiment ran in this lane. This construction is technically motivated by existing APIs, while note ownership, static-call effects, max-fee charging, replay/revert persistence, default setup acceptance and client-root integration remain executable feasibility gates before adoption.
