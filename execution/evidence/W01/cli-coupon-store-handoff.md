# Durable CLI coupon store

`sponsor-service/coupon-store.mjs` exports `createSqliteSponsorCouponStore({dbPath,encryptionKey,maxRecords=64})` and the existing fixed-code `CouponStoreError`. Await creation. It returns the matching async `pending({partition,nowSeconds})`, `put(record,{nowSeconds})`, `markAttempted(id)` interface plus `close()`. It uses actual Node24 SQLite, not fake IndexedDB. This file is CLI-only and must not be bundled into the browser SDK.

The caller must supply a genuine AES-GCM CryptoKey with encrypt/decrypt usages. Non-extractable keys are supported; the store never exports, persists or logs the key. Key derivation/recovery/unlock remains caller-owned. Payloads are JSON, limited to8192 UTF-8 bytes, encrypted with fresh96-bit random IVs and AES-GCM. AAD binds the shared version domain, ID, partition, expiry and attempted flag. Only opaque ID/partition, expiry and attempt state are plaintext metadata. An independently domain-separated encrypted key check binds the configured record limit and rejects a wrong key even when the database contains no coupons.

The absolute canonical database path must have an owned private directory and an owned0600 regular single-link database. Direct/ancestor symlinks are rejected through canonical directory validation; existing unrelated directories are never chmodded. Existing journal/WAL/SHM files must also meet private file checks. SQLite uses DELETE journals, FULL synchronization, trusted_schema=OFF and a5-second lock wait. All SQL data arguments are parameterized; schema/table statements are fixed constants.

Every operation authenticates the complete bounded snapshot (at most64 records) before acting, including expired and attempted records. This prevents tampered expiry or attempted metadata from silently hiding/deleting a row. SQL checks bound record counts and blob/text lengths before fetching payloads. Mutations then acquire BEGIN IMMEDIATE and compare the complete snapshot plus key metadata before pruning, insertion or attempt marking. Crypto awaits never hold SQLite write locks. A changed snapshot fails closed; competing attempt markers return exactly one true, and callers must not send after false/error. A committed pending result can naturally become stale when another process acts afterward, so marking attempted remains mandatory immediately before use. At expiry equality a record remains retained; it is removed only when expiry is less than the supplied current time. Attempted rows remain until expiry and still count toward the cap. A full store with no matching pending coupon rejects fresh acquisition, matching the browser interface.

Validation: **16/16 passed** with pinned Node24.21.0, actual SQLite files and actual AES-GCM. Tests cover restart/decryption, plaintext absence in database bytes, double-attempt rejection after reopen, wrong key with empty/populated database, bad key algorithm and policy drift, six metadata/ciphertext tamper cases, atomic duplicate insertion across separate connections, double attempt across separate connections and two actual child processes with a startup barrier, capacity/expiry behavior, malformed and oversized records, unsafe times, private directory/file/symlink/hardlink checks, and oversized stored ciphertext. Child processes have10-second hard-kill supervisors; both completed normally. Tests use a clearly fixed synthetic key only in the competing-process fixture. Temporary files/connections are closed and cleaned; no network/build/proof work was run.

Limitations: this is a storage adapter, not CLI key-management or provider integration. The key must remain available through the caller's secure unlock mechanism across restarts. Opaque partition metadata can permit local dictionary probing if an observer already knows candidate owner/scope values; disk encryption does not hide access patterns or metadata. A privileged process with the live key or same-user memory access can recover plaintext. Whole-database deletion, consistent replacement or rollback of previously authenticated ciphertext is not detected without an external durable/chain anchor. No tamper-proof or rollback-proof claim is made. The store's cap bounds active records, not total historical SQLite disk size, filesystem capacity or secure erasure. Production backup, disk monitoring, host permissions and retention remain operator work.
