# Shared fee observation assessment — engineering checkpoint

This assessment uses the P01 observer model and current local source/tests. It is not a completed W01/T03 privacy qualification or a claim of network anonymity.

| Observer | Visible data and present boundary | Evidence and remaining qualification |
| --- | --- | --- |
| Public chain observer | Sponsor address pays author transactions. Shared replenishment starts at the operator's L1 fee-token account and credits the sponsor; it does not fund each author account. Batch administration exposes batch ID, root, fixed window and allocated count. Posts, timing, L1 deposit/exit bookends and ordinary transaction effects remain observable. | Genuine claim/exit and posting milestones verify actual sponsor payer, exact fee debit and zero author FeeJuice. Current delivery work registers a common batch. Full repeated-action effect/linkability analysis remains T03/W01 work. |
| Coupon issuer | Reserve carries only window; submit carries retrieval token and opaque leaf; retrieve carries token. The token deliberately links that issuance's requests to one another. No owner, blind, action kind/content, wallet keys or auth witness is transmitted by these interfaces. | Actual HTTP/core/provider delivery test checks exact received field sets. Commitment hashing includes a fresh private blind and domain/network/sponsor/batch/index/owner binding. Issuer storage retains only token hashes, leaves and paths. Endpoint/proxy connection metadata and request timing still correlate requests. |
| RPC provider | Receives wallet/node reads and transaction submissions, with source IP/timing. Public batch queries reveal requested batch IDs. Static sponsor configuration/class checks occur before authorization. Local proving does not make node access patterns anonymous. | Read-only helper has no signing capability and passes actual ABI/class/address checks with provider doubles. Full genuine request-method/parameter observation is still required; do not assert all RPC queries are unlinkable. |
| Frontend host / injected script | Host sees page/asset requests. Code executing in the unlocked page can access wallet operations and coupon plaintext. Encryption at rest does not defend against a compromised served application or same-origin script. | No remote coupon callback is allowed by the routing design; a trusted local provider receives owner/action metadata. Release asset integrity, host headers and browser threat checks remain downstream gates. |
| Local storage observer | Encrypted coupon payload contains owner, blind and retrieval token. Plain metadata includes opaque record/partition hashes, expiry and attempted state. A known-owner/scope dictionary can probe the partition hash; timing and disk access are not hidden. | AES-GCM authenticates record metadata; actual browser/SQLite tests cover reopening and atomic attempted state. SQLite authenticates all rows before pruning. Whole database rollback/deletion, live-key compromise and filesystem access patterns remain outside the storage assurance. |
| Sponsor/operator | Public administration and aggregate allocated/submitted/sealed/reserved counters; shared fee balance and receipts. The operator need not receive an author account to allocate a coupon. | Core caps liability per fixed window and never refunds missing/unused slots into that window's allocation. HTTP global admission uses no per-user/IP identity map. Replenishment/outage automation, durable registration recovery and service deployment remain incomplete. |

The RPC API key is a frontend-visible configuration value, not an application secret. The restricted fetch wrapper attaches it only to the exact configured origin/path, preserves caller headers and rejects redirects. A generated-page test reproduced a second unsafe legacy wrapper; it was removed. The issuer now also rejects a misplaced `x-aztec-api-key` before allocation. These controls reduce accidental disclosure; they do not make browser-held credentials confidential.

Shared batching does not by itself establish a measured anonymity set. The first genuine milestones used one-leaf test roots. The two-client HTTP integration demonstrates a common root with distinct private coupons, but has a chain callback double. The new genuine delivery harness uses two coupons for one author in separate test stores; that is delivery/accounting evidence, not multi-user anonymity evidence. Population, issuance timing, batch selection and post content remain material.

Current service controls deliberately trade availability for bounded liability: global rate limits can be exhausted by an adversary, and lost reservation replies leave charged orphan slots. No owner collection or per-author funding fallback is introduced to recover them. Deployment must describe this denial-of-service boundary honestly and qualify operator recovery before W01 closes.
