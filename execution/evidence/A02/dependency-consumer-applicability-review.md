## Jaeger high advisory: actual narrow fix, not startup-only exclusion

The preserved pre-fix controls show that installed Jaeger 1.30.1 throws on a tiny malformed encoded header and that a preinstalled global Jaeger propagator survives Aztec no-op startup. Those exceptions were caught in isolated test processes. They establish the limit of a clean-startup-only argument, not an application endpoint exploit.

Root instead selected **Jaeger 2.9.0 with its own nested core 2.9.0**, retaining SDK-trace-node and root core **1.30.1**. Final tests independently verify exact resolver identities and the common API **1.9.1** resolution; no broad OpenTelemetry upgrade or local node_modules patch is assumed.

The actual updated propagator ignores malformed default trace and baggage headers, including an array header, while preserving a valid baggage sibling. Default and custom trace/baggage header round-trips remain correct. Suppression applied with root core 1.30 is honored by Jaeger's nested core 2.9. Actual SDK 1.30 environment-selected Jaeger registration works; the preloaded-global/no-op case that formerly threw now ignores the same malformed input. These checks exercise the runtime interfaces across the targeted major override.

The publisher describes opt-in active Jaeger decoding as the high advisory condition and identifies **2.9.0** as its fix. [Publisher GHSA-45rx-2jwx-cxfr, published July 3, 2026](https://github.com/open-telemetry/opentelemetry-js/security/advisories/GHSA-45rx-2jwx-cxfr), rechecked September 14. The selected fix removes the need to claim all earlier instrumentation unreachable for this issue. It does not by itself prove every native/browser/prover compatibility requirement; root retains those broader checks and the final advisory inventory.

## W3C Baggage moderate advisory remains separate

The root core 1.30.1 and other existing older core copies were deliberately not upgraded. The publisher's **W3CBaggagePropagator** advisory is different from W3C **TraceContext**; the fix is **2.8.0**. [Publisher GHSA-8988-4f7v-96qf, published June 12, 2026](https://github.com/open-telemetry/opentelemetry-js/security/advisories/GHSA-8988-4f7v-96qf), rechecked September 14. Nested core 2.9 under Jaeger does not repair those other copies.

Actual clean Aztec no-op and enabled initialization were exercised with `OTEL_PROPAGATORS=jaeger,baggage`. Enabled Aztec explicitly selects TraceContext only. Tests check the exact active fields, a real valid traceparent round-trip and malformed trace handling; a getter that throws if baggage is read proves that this path does not extract baggage. The Jaeger extraction method is instrumented only in memory to assert zero decoder calls in that path.

That is an enforceable regression of the tested Aztec startup, not a universal exclusion. No-op startup does not sanitize arbitrary previously registered propagators. Generic OpenTelemetry registration, a future baggage-enabled service or a preloaded Baggage propagator remains outside this claim. Any retained moderate disposition must identify the exact supported service/startup profile, transport/header controls, owner and re-review trigger in root's residual inventory and release packet. Enabling baggage or changing initialization invalidates this scoped observation and requires compatible remediation or explicit bounds/renewed review. This lane does not approve a blanket all-core exception.

## History, integration and remaining acceptance

The first sandboxed attempt retained listener EPERM failures. One valid temporary-file assertion also compared macOS /var and canonical /private/var spellings; the fixture was corrected to canonicalize its own root. The first scoped run then passed 25 tests; three additional small transport controls produced the preserved 28-pass run. The Jaeger update replaces known-bad assertions with fail-closed/compatibility checks, producing the final 31-pass run. Earlier logs/context and the complete pre-fix telemetry test source are preserved; no historical result was rewritten.

Telemetry tests use fresh child runtimes with a 30-second timeout, bounded output and SIGKILL followed by execFile callback completion if needed. The observed successful children and final suite exited naturally. Temporary files, Agent connections, WebSocket clients/servers, telemetry providers and loopback collectors have explicit cleanup. This is recorded lifecycle completion, not an OS-wide orphan-process audit.

I also read root's ten qs/UUID tests and their verified-old-source baseline report: the bounded valid/invalid controls and actual CommonJS caller resolution address the described parser and buffer boundaries without large inputs. No blocking source-review issue was found. That lane's execution/provenance evidence remains its own; this review did not rerun it.

Suggested root script integration: run all `scripts/test-dependency-*.mjs` with Node's test runner and concurrency one under the pinned runtime. Root still needs affected SDK/build/browser/provenance checks, final exact-lock audit and independent residual disposition. The previous P04 browser manifest exclusion observation must be refreshed after the new lock/rebuild. Overrides do not rewrite dependencies already embedded in minified TXE or other published bundles; the separate packaging inventory must retain those tooling/isolation limitations rather than claiming them patched by npm resolution alone. No independent claim about those bundled bytes is made here.

External review, genuine proof journeys, network clearance and the later production gates remain required. This report supports bounded dependency compatibility/remediation assessment; it does not mark A02 or the application production-ready.
