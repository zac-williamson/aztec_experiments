# Derived CRS build implementation

The schemaVersion2 manifest adds a required, locally derived 72 MiB BN254 G1 asset. The original three downloaded assets, URL/range/format/capacity/length/checksum pins are unchanged. Network assets retain the 64 MiB per-asset cap; the derived output has a separate exact 75,497,472-byte pin and is never fetched by the build downloader.

The build verifies the installed Aztec package versions, pinned downloader source, actual compressed WASM archive bytes and all source asset bytes. A child process explicitly selects `BackendType.Wasm`, repeats source/WASM checks, invokes `srsInitSrs` on the compressed G1/G2 inputs and verifies the complete returned derived bytes before writing a unique temporary file. The parent accepts that result only after successful child closure and another full file length/checksum check. Reusable cache and target files are read and verified completely. Corrupted caches/targets are repaired from another verified source or a fresh derivation; unverified bytes are not promoted.

Every asset and final manifest write uses an exclusive unique temporary file, re-verifies that file and renames it atomically. A failed rename or corrupt temporary write leaves the previous target unchanged and removes its temporary file. The final manifest is written only after all source and derived assets are verified. Application assembly verifies the derived asset, and the reproducibility comparator includes its entire contents, raising the expected output inventory from33to34files.

The synchronous WASM operation runs outside the parent's event loop. Its default build deadline is600seconds, followed by a bounded3second wait for closure after SIGKILL. Parent SIGINT/SIGTERM also terminates the child. Focused tests use real harmless child processes to verify normal timeout/interruption closure and restored signal listeners. If the OS refuses to close the child within the kill-wait bound, the helper reports an explicit teardown failure; it does not claim successful reaping in that exceptional case. This is a build supervision budget, separate from browser/product deadlines.

`wasmSha256` binds the compressed file identified by `wasmSource` (`barretenberg-threads.wasm.gz`), not the decompressed WASM bytes. `derivation.method = bb-srs-init-v1` names the JS procedure; the manifest does not independently hash that glue code. Its exact source is bound by `derived-crs-build-implementation.json` and must be included in the final candidate source inventory/review evidence. Package installation and source snapshots remain part of the trust boundary.

Focused verification: Node24.15.0 ran `node --test scripts/test-crs-build.mjs`:33passed,0failed. Tests exercise source/output/provenance mismatch, network streaming bounds, corrupted cache bytes, atomic write failures and child timeout/interruption. Worker/application scripts pass syntax checks. These tests do not execute the full BN254 derivation or establish setup/proof soundness. Full new-worker derivation, integrated build, browser verification and independent fresh Linux derivation remain for root integration. The separate recorded experiment is the origin of the proposed output pin; no experimental output was copied into production caches by this lane.
