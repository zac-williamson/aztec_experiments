# P04 CRS migration review

The isolated native build reproduced a real integration failure: toolchain 5.2.0 rejected a CRS manifest still declaring 5.0.0. The failed command/log is preserved in `clean-native-build.log`; no version check was bypassed. Root corrected the manifest only after the following checks. A later actual browser check independently found the runtime validator's remaining 5.0 version check; root corrected that and added a mismatched-version regression. The clean copy received both changes with explicit delta records.

## Verified compatibility facts

The fresh npm installation and root installation both contain @aztec/bb.js 5.2.0. Their `dest/node/crs/net_crs.js` SHA-256 is `98182144b264c587733e40e5ed22446d704af132eb36ed0b02b307a99cda4da5`, exactly the downloader source hash recorded in the earlier 5.0 manifest. The official tagged package's source retains both official hosts, compressed BN254 G1 at 32 bytes/point, G2 data, and Grumpkin v2 at 64 bytes/point.

`src/barretenberg/index.ts` calls actual `srsInitSrs({pointsBuf,numPoints,g2Point})` and explicitly documents 32/64-byte autodetection, followed by `srsInitGrumpkinSrs`. The browser cache slices uncompressed G1 to exactly `numPoints*64`; the compressed supplied bytes use the manifest's matching point count. The SDK's default Chonk G1 capacity is 2^19 points (2^18 for iOS), and its Grumpkin request is 2^16. Our provisioned 1179648 and 65537 points exceed those defaults. This is format/default compatibility, not proof-workload capacity or mobile feasibility.

I invoked the maintained `downloadCrsAsset` independently against each manifest entry, with no target/cache reuse. That function requires HTTP206, exact Content-Range and bounded streamed bytes, then SHA-256 verification. `crs-official-reverification.json` records actual fresh results and configured official hosts; it does not assert which host served a fallback. The later corrected isolated `build:crs` independently provisioned fresh local outputs and passed all three hashes, as recorded in `clean-native-build-recovery.log`.

- `g1.dat`: 37748736 bytes, 1179648 points, `bn254-g1-compressed-32-byte`, range 0–37748735, SHA-256 `8d6fb7829bcfbfeaf02a79104539bfd3777a328ec46d3331e37effca2ee1b416`; official primary https://crs.aztec-cdn.foundation/g1_compressed.dat.
- `g2.dat`: 128 bytes, 1 points, `bn254-g2-uncompressed-128-byte`, range 0–127, SHA-256 `01797bfc4de5a96f0e516a9ea4537d18786dc30cb991aca4274c95822b69c32f`; official primary https://crs.aztec-cdn.foundation/g2.dat.
- `grumpkin_g1.dat`: 4194368 bytes, 65537 points, `grumpkin-g1-v2-uncompressed-64-byte`, range 0–4194367, SHA-256 `b4988c0ae3dd058b781045aeb70000d7b7fb5ffe557ed4f81c64b437c39a61c9`; official primary https://crs.aztec-cdn.foundation/grumpkin_g1_v2.dat.

## Limits

No proof was generated by this review. Actual browser SRS initialization is root's separate evidence, and still does not establish production proof validity, sufficient capacity, external audit or target-network clearance. The pins are locally recorded hashes of official downloads, not an independent publisher checksum attestation. Native builds share the existing verified Noir source cache and installed Foundry/Solidity tools; no claim of an empty host cache is made.
