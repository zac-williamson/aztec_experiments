## Concrete bundle composition

The current `aztec_bundle.js` is **50,130,889 bytes**. `build-sdk.mjs` produces a non-minified IIFE from `shared/sdk-entry.mjs`, using `@aztec/pxe/client/bundle`; it does not enable code splitting. The build asks esbuild for metadata, then uses its input/output names to construct `sdk-manifest.json` and discards the actual metafile. The saved manifest has 1,361 source hashes and eight output hashes, without per-input retained-byte attribution. Across packages, 66 artifact-labelled sections occupy approximately37,931,979 bytes (75.7%). Large individual examples include `private_kernel_reset_tail_to_public.json` (~1.95MB), `HandshakeRegistry.json` (~1.81MB), `SchnorrAccount.json` (~1.68MB) and `private_kernel_reset_tail.json` (~1.61MB). These include circuit bytecode and metadata, not merely whitespace or debug logging.

Two Barretenberg browser source modules contain gzip/base64 data-URL strings of roughly4.10MB and4.14MB. Their generated sections together occupy8,234,891 bytes (~16.4%). They are the shared-memory and nonshared-memory WASM variants. The pinned browser loader deliberately selects between them; they are not interchangeable accidental duplicates. The `.wasm: binary` build setting is not itself the source of these two strings: they already exist in the upstream JavaScript modules. ACVM, Noir ABI and SQLite WASM are separately copied runtime assets in the current build.

Twenty manifest inputs use nested dependency paths (principally different resolved crypto-library dependencies). Repeated generated source labels also occur where esbuild separates declarations and initialization; a repeated label alone is not duplicated module execution. No large accidental duplicate was established, and the observed dominant data is sufficient to prioritize artifact/WASM loading before arbitrary dependency deduplication. Protocol reset variants and account artifacts must not be dropped merely because names look similar.

## Supported optimization paths, not yet measured

**Largest potential scope: use the supported lazy PXE providers with actual code splitting.** The pinned package exports `@aztec/pxe/client/lazy`. Its `utils.js` selects `BBLazyPrivateKernelProver`, `LazyProtocolContractsProvider` and lazy standard preloads. The protocol-artifact helper contains explicit dynamic imports for the requested circuit. This can defer artifacts until needed, but switching only the import path is insufficient: esbuild includes dynamic imports in the same file unless splitting is enabled. Splitting requires ESM output and an output directory. [Official esbuild splitting documentation](https://esbuild.github.io/api/#splitting).

A maintained ESM entrypoint and explicit readiness boundary across current app/CLI consumers would replace assumptions that `window.__aztec` exists synchronously after a classic script. Keep the required SDK exports and real provider implementations. Separately exported account/FeeJuice artifacts and other static dependencies may still be eager; the exact saving must come from a new metafile and network trace, not subtracting all75.7% as guaranteed savings. This is a coherent future frontend/build change, not appropriate to slip into the active frozen verification run.

**Smaller isolated scope: move the two BB payloads out of the first script.** The pinned browser `fetchCode(multithreaded, wasmPath)` supports an external URL and adds `-threads` to its basename when shared memory is available; otherwise it selects the embedded dynamic-import payload. Correctly deployed same-origin `barretenberg.wasm.gz` and `barretenberg-threads.wasm.gz` assets could preserve both exact payloads. Passing `wasmPath` at runtime alone does not remove the fallback module imports from the current IIFE. Removing their initial bytes needs supported ESM splitting or a narrowly verified build-time module/URL relocation, with every output derived from locked package bytes and included in the manifest. Do not delete a fallback variant or use an unpinned CDN.

All singleton, worker and async initialization paths would need consistent URL configuration; the loader's filename rewriting must be tested explicitly. Decompressing the WASM file remains separate from compiling it and from SRS initialization. This proposal addresses initial JS delivery/parse work, not proof cost or derived-G1 correctness.

Minification and HTTP compression can reduce transfer/formatting overhead but do not remove the embedded artifact/base64 payloads or make all runtime initialization lazy. No size/speed claim is made without a build and actual measurement.

## Required verification before adopting either path

First persist the real relative-path metafile from an authorized build; it provides `bytesInOutput` and dependency imports for accurate comparisons. [Official esbuild metadata format](https://esbuild.github.io/api/#metafile). Preserve current source hashes, lockfile/build-script binding, and exact output hashes for **every** emitted chunk, worker and asset. `check-sdk.mjs` currently confines outputs to flat filenames, and `build-sdk.mjs` reduces output paths to basenames: any nested chunk layout requires explicit safe-path/collision handling rather than silently flattening files. `apps/build.mjs` already copies all manifest output names, but its copy path and standalone browser/CLI loaders need renewed tests.

Retain origin-isolation headers, actual worker initialization/destruction, SQLite/ACVM/ABI assets and both CRS consumer checks. Verify missing/corrupt chunks fail visibly, allowed assets stay same-origin and deployment publishes a coherent version. Run real lazy circuit/provider paths rather than only checking export names; add actual cold/warm request and readiness measurements plus current proof-workload gates. An imported but never exercised chunk is not qualified. No arbitrary timeout increase is recommended.

The prior navigation trace proves that this large script must be delivered and executed before the evaluation timer starts. Its size/composition supplies concrete optimization targets; it does not establish which internal operation caused a particular timeout or how fast a revised bundle would be.

## Root privacy handoff

A design inference to evaluate before adopting lazy artifact requests: an asset host can observe requested paths and timing. Fetching a function-specific circuit only when preparing its proof may reveal the operation type/timing to that host, even if the chain transaction hides author identity. This has not been measured as an exploit or asserted as a current leak; the current eager payload does not use the proposed per-operation request pattern. A01/U01/T03 must compare request footprints, grouping or uniform prefetch, browser caching and hosting logs against the declared observer model. Smaller initial payload alone is not sufficient acceptance for an anonymous application.
