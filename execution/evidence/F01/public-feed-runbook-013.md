# Public message feed

Open `feed.html` to read without loading a wallet, private account, PXE, contract
bytecode, SDK bundle or proving assets. Supply the portal and public Ethereum/Aztec
endpoints. The reader checks the Ethereum chain, portal's board/rollup/version,
the pinned original/current board class and corresponding immutable public L2
configuration. It uses checkpointed state, which is still subject to reorganisation;
this is RPC-based public reading, not independent consensus or inclusion-proof
verification. RPC operators observe requests and public board identity.

The same reader supplies the user/moderator message panels (latest50 posts, link
to older pages) and `cli.mjs list --json`. Listing does not read wallet files,
load private account state or prepare fees. Its existing moderation consumer gets
public policy/post data; durable queue/policy-per-job handling remains M02. Signing
still performs its own current authority, policy and post checks. The local public
cache is not trusted signing evidence.

## Progress and reorganisation

Three event tags cover publication, policy and flags. Each RPC page contains at
most20 logs, each complete range at most100 RPC pages/2000 events. The index reads
50-block ranges, up to4 per update under one20-second read budget. Each range is
committed atomically only after complete event paging and canonical block checks.
Publication orders must be contiguous from zero and every post must have its
policy; duplicate or conflicting identities cannot advance the checkpoint.

On restart the last checkpoint is rechecked. A reorganisation discards affected
pages/events and invalidates pagination cursors. After128 unsuccessful checkpoint
comparisons the public index resets and backfills from block1. Missing checkpoints
or unavailable RPCs retain the old state and report an error rather than claiming
success. A page cursor fixes its maximum publication order so newer arrivals do
not cause duplicates or omissions; refresh starts a new view. Moderation changes
remain current. Same-height reorganisations invalidate the cursor too.

First-time history loading is intentionally bounded. Refresh continues a saved
backfill; CLI listing exits with a backfill message until history is complete, so
moderation cannot treat an incomplete list as complete. No network prover runs.

## Storage, retention and capacity

The browser uses only IndexedDB `aztec-billboard-public-feed-v1`; the standalone
reader never opens a private database. Cached records contain strictly validated
public event payloads, scope, chain positions and canonical checkpoints. No wallet
keys, private notes, fee claims, deposit secrets or telemetry are stored. Malformed
or unexpected fields fail validation. Public content can still be sensitive to a
reader: clear this site's browser data to remove its local copy.

The CLI uses `.public-feed-cache/`, separate from wallets and recovery journals;
`--public-feed-cache` selects another directory. Files use private permissions,
exclusive update locks, atomic replacement, fsync and compare-and-swap. This is
public JSON, not encrypted custody. After a crash, inspect any lock and confirm
its owning process is gone before removing that specific lock. Do not remove a
wallet journal. Deleting this disposable public cache causes a complete backfill.

The default cache retains all indexed public history, up to50000 events and20000
range checkpoints. The file adapter also caps each record at32MiB; browser storage
quota may be smaller. Capacity/quota failure is explicit and leaves the prior
checkpoint intact. There is no silent pruning of posts or moderation context.
Larger deployments need a deliberately sized public index and corresponding
qualification; these defaults are limits, not a claim of unlimited scale. Browser
connections retain one active board and one database handle to bound session memory.

Build metadata and the23KB reader bundle are generated by the canonical app build
from pinned event ABIs, tags, contract class and storage layout. The frontend
manifest binds these public outputs and inputs. The actual browser/CLI check uses
controlled RPC responses, not a live public network. Release T05 must reconcile
all checks against its final candidate; external audit/soak remain separate gates.
