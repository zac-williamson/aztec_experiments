# Claim inclusion failure — source-backed timing diagnosis

Read-only review of `real-network-c40e5544-d29c-49ce-bc37-7c2b3dce5fd4.json` and installed sequencer/publisher code. No rerun, source modification or chain call in this lane.

**Observed:** the run failed at `c01-deposit-flow.mjs:159`, after the ordinary inclusion wait, with stage `include-real-claim`. Reaching that point requires a genuine nonempty private proof, an unchanged selected anchor, normal `node.isValidTx(...).result === 'valid'`, and `node.sendTx`. It does not establish successful inclusion. Ready had already settled/activated; the real deposit event recorded L1 block 1109. Final logs show previous-L1-block wait timeout, slot 107 publication failure, pruning after L2 block 5, then discarded pipelined work because parent checkpoint 6 did not land on L1. Peak sampled descendant RSS was 6,832,512 KiB, with no RSS sampling error or parent stop reason; descendant and temporary-directory cleanup succeeded. This is not evidence of a proof rejection or memory-limit failure.

**Concrete likely harness cause:** L1 mining is driven only by awaited `mine()`/`tick()` loops. After obtaining the Inbox anchor, the claim helper restores ordinary sequencer settings and then awaits expensive PXE proving and node validation without mining L1. The sequencer/publisher continues running. Installed `TestDateProvider.now()` is `Date.now() + offset` (`foundation/src/timer/date.ts:26–31`); setting it once does not freeze it. Thus publisher wall time can cross multiple L2 slots while no ordinary L1 blocks are produced. Already-started empty-checkpoint jobs are not stopped by restoring configuration: sequencer `updateConfig` replaces the config object, and each existing CheckpointProposalJob already holds its own supplied config reference.

The observed failure chain matches this gap. `sequencer-publisher.ts:646–697` waits until the target-slot boundary minus one Ethereum slot, then polls actual latest L1 timestamps. Default `sequencerPublisherPreviousL1BlockWaitTimeoutMs` is 8,000 (`publisher/config.ts:182–191`). If L1 never mines that predecessor, advancing DateProvider reaches the timeout and publication proceeds anyway. `checkpoint_proposal_job.ts:369–400` binds proposal submission to the last Ethereum block inside the target L2 slot. The harness uses 12-second L2 slots and 1-second L1 slots, so a genuine client proof can outlast this timing window. The later parent-checkpoint check (`checkpoint_proposal_job.ts:440–495`) correctly rejects pipelined work whose parent never became canonical; that rejection should not be bypassed.

**Limit of diagnosis:** the retained sanitization removed publication receipt fields and timing context. The text “failed with no error message” comes from the publisher's actual receipt callback when no `CheckpointProposed` success event is found (`sequencer-publisher.ts:1440–1485`). It is not a decoded Solidity error and does not by itself prove an expiration revert. The original L1 transaction hash/status, mined timestamp, target-slot timestamps and inner-forwarder failure reason are missing, so this remains a high-confidence timing hypothesis, not a reproduced exact EVM cause.

**Minimal next harness correction:** keep ordinary L1 mining alive while genuine client proving/node verification is awaited. Use a single serialized, bounded asynchronous loop at the declared one-second cadence, synchronize only to actual mined timestamps, and await its complete stop before returning to the existing manual inclusion loop. Propagate mining errors, retain the current proof/anchor/admission checks, and avoid two concurrent mining loops that accelerate the chain accidentally. Start this keepalive before the first potentially long proof call once Inbox/eligibility waiting has ended; the same issue applies to the later exit proof. If wallet initialization itself spans active publisher work, cover that phase too. A single lifecycle-owned miner across the bridge would also address all gaps, but requires existing loops to stop issuing duplicate mines. Do not freeze only the node clock, widen publication validity, set parent-validation bypasses, fabricate roots, or extend the inclusion deadline as the purported fix.

Useful discriminating evidence for the next run: bounded samples of actual L1 block number/timestamp and DateProvider timestamp during each proof; claim tx hash and admission status before send; canonical receipt statuses while waiting; slot/target/previous-L1 timestamps for the first publication timeout; actual failed L1 receipt hash/status/block timestamp and decoded safe error category where available. Keep calldata, proofs, witness inputs and keys out of records. Passing genuine inclusion after continuous ordinary mining would support the hypothesis; a repeated failure with coherent timestamps would require the actual publication receipt diagnosis before further changes.
