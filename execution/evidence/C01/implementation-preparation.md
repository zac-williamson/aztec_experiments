Read-only handoff, 2026-09-12. Inspected the C01 graph plan, current Noir/portal sources, frozen P04 contract/service interfaces and actual pinned Aztec 5.2.0 APIs. No production code changed and no heavy test or chain run was started. This document does not mark C01 started or passed.

## Implementation target and present gap

C01 owns authentic collateral claims, receipt identity and message separation under REQ02/B03. The target is `execution/interface-spec.md` sections 1–4 and the relevant claim/exit portions of section 8. Fresh deployment permits replacing the old ABI and note layouts; do not introduce compatibility aliases, duplicate claim paths, old-state migration or a permissive transitional production deployment.

The current `claim_deposit` consumes a message against a **caller-supplied portal**, reads only cooldown/minimum historically, and mints the seven-field legacy DepositNote. The current portal accepts deposits immediately, has no maximum configuration/receipt nonce, and hashes only depositor/amount. Portal binding is one-time but accepts zero and emits no Ready message. Existing withdrawal emits the old two-field hash and reads an arbitrary first owned deposit note. These are source observations, not newly reproduced exploit claims.

## Ordering and decisions to resolve before implementation

1. **Preserve graph gates.** P04 must finish before C01 begins. Refresh graph validation/next selection and record actual ownership. Source edits here span interdependent Noir and portal ABIs; use separate helper/test review lanes with one owner for each production file.
2. **Define the exact configuration ABI.** P04 intentionally gives logical types, not a finalized constructor/getter order. Decide one shared order/naming, immutable storage primitive and scope getters. Full configHash cannot be precomputed before the deployed board address exists; board initialization may compute it with `this_address`, and D01 reads/recomputes it before constructing the portal. Never reintroduce the portal-address cycle.
3. **Activation visibility is asymmetric.** L2 binding establishes its portal and sends Ready. L1 becomes active only after consuming Ready. L2 cannot infer L1 activation merely from its own boolean, and no extra L1→L2 activated acknowledgement is specified. Claims require complete **L2 binding** plus an authentic portal claim; the portal itself gates deposits on activation. Do not invent an unprovable historical L1 boolean read or an administrator exception.
4. **Schema staging needs an explicit root decision.** C01's claim must produce the final 11-field note, while old post/withdraw code assumes seven fields/global indexes. Adopt one fresh schema and authorize the minimum coherent constructor/query/carry-forward changes in C01, with a recorded list of C02–C05 semantics still pending. If maintaining a compiling intermediate version requires substantive later-package semantics, revise package ownership/dependencies explicitly instead of introducing a legacy-compatible second note or claiming unchanged flows work. Deployable candidate status stays false until the chain is integrated.
5. **Initial cooldown has a cross-package dependency.** Current `compute_cooldown` floors division; the target uses ceiling. C01 initial-right acceptance must use the target rounding/checked sum. Agree whether C01 owns the shared narrow cooldown fix and its tests, while C05 retains burst/penalty/horizon qualification; avoid silently changing C05 scope or blessing floor rounding in C01.
6. **Replay acceptance overlaps C06/T02.** C01-A03 explicitly includes repeated withdrawals; P04 also requires a real Ready/claim round trip. Decide the minimum actual-chain receipt/no-post exit harness necessary for C01 and reserve broad accounting/reentrancy/economics for C06. Do not mark all C01 acceptance complete solely with TXE insertion and permissive bridge mocks. If the proof environment is unavailable, retain the criterion as incomplete and record its concrete prerequisite rather than simulating acceptance.
7. **Consumer handoff must be intentional.** New events, getter shapes and constructor/claim/withdraw arguments invalidate current CLI/browser/deployer assumptions. C01's listed edit boundary does not include app sources. Record an approved minimal ABI-consumer adapter expansion or downstream incompatibility gate before editing them. Rebuilding stale artifacts alone does not migrate runtime consumers.

## Meaningful regression controls

| Acceptance | Required normal and rejecting controls |
| --- | --- |
| A01 intended collateral | Real portal deposit at min/max creates one receipt/message; one private claim creates exactly one owned V1 right with exact nonce/amount/ancestry and initial eligibility. Different owners knowing distinct secrets receive separate rights. Read/authenticate the produced state rather than counting a successful call alone. |
| A02 origin/config | Correctly bound control first; then wrong portal sender with otherwise valid message, wrong recipient board, wrong chain/version envelope, changed depositor/nonce/amount/content, wrong/zero secret, zero/oversized address, unset binding and out-of-range deposit. Each must fail at its intended check without a consumed message or usable minted right. Distinguish a malformed config rejection from proof of envelope authentication. |
| A02 activation | Deposit before Ready fails; authentic Ready activates once; changed board/version/portal/chain/configHash/domain or invalid path fails; direct public setter and non-deployer private binding fail; zero/rebind fails. Outbox failure must leave activation false. |
| A03 uniqueness | Claim same message twice, including concurrent preparation and altered owner, creates no second right. Deposit→claim→burn→refund→redeposit increments nonce, changes claim/exit contents and depositChainId even for the same depositor/amount. Prior exit proof cannot pay the later nonce; an already consumed proof cannot pay again. Duplicate active L1 deposit rejects; failed deposit leaves nonce/counter/liability unchanged. |
| A03/A04 conservation | Rejected claim leaves no usable note; failed public exit does not burn a right irrecoverably or emit a spendable exit. Failed Outbox consumption/ETH receipt rolls back active receipt and total; successful release burns L2 rights before L1 payment. Strict bridge mocks can test rollback logic, actual protocol and proof-enabled cross-chain runs establish authentication/atomicity. |
| A04 byte agreement and baseline sensitivity | Call actual production codecs against all seven frozen SHA vectors plus leading-zero and boundary values. Mutate each scope/receipt field independently and verify mismatch, without relying only on collision inequality. Retain known-bad artifacts as historical controls; relevant wrong-origin tests should reject the repaired code and demonstrate the old boundary where practical. Run full affected Noir/portal suites after helper migration and document intentional V1 changes to old expectations. |
