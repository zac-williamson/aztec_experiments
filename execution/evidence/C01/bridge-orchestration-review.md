**Actionable serialization gap:** `stopIdleAgent()` checks `getStatus()` before stopping, but only `isRunning()` afterward. Installed `ProvingAgent.stop()` aborts the current controller before awaiting `runningPromise.stop()`. Meanwhile `work()` can be awaiting broker acquisition or proof-input loading with no current controller yet; after the pre-check it can still create/start a proof before the running loop finishes stopping. Thus polling can be stopped with a live proof, invalidating the claimed client/server serialization. Require `agent.getStatus().status === 'stopped'` after the awaited stop, before any client proof or refund. Fail closed to parent cleanup if that check fails. Do not treat another abort call as proof completion: controller abort does not await native completion, and its completion callback can call `RunningPromise.trigger()`, which directly invokes work while polling is stopped. This source-derived race was reported to root; no race reproduction was run.

Exact installed paths: `@aztec/prover-client/src/proving_broker/proving_agent.ts` lines 49–72 (status/lifecycle), 120–164 (asynchronous acquisition/controller creation/completion callback); `proving_job_controller.ts` abort/run; `@aztec/foundation/src/promise/running-promise.ts` lines 90–96 and 117–120. Source hashes respectively `f5f3167ad42fa8d57f895357161274c6162c10779e3b04628f17c533b4aa6bf4` for proving_agent and `d3a66ede2fd91e0e5da1789711eb7e8bfbb9ac9fda64a79b41b191ef2597d7da` for running-promise.

Other checked integration agrees with installed interfaces: `ProverNode.getProver()` returns the ProverClient; its emitted JavaScript `agents` array is a test-only internal seam. Agent `start()` is synchronous and RunningPromise supports restart after awaited stop. The bridge does not call `ProverClient.stop()`, which would also cancel queues/facades and is unsuitable as a pause. Ready starts the ProverNode service once; exit reuses it through `startProver:false`. Nonenumerable claim/exit/witness contexts remain accessible in memory while excluded from ordinary result serialization. Errors from all four stages map to their actual observation property names.

The Ready wrapper passes the real portal-deployment block to the generic proof search, binds the supplied Ready inclusion tx hash and block number, uses the actual returned witness in `activate`, and requires successful canonical L1 activation plus enabled portal state. The bridge passes the actual exit tx hash and expected leaf to generic settlement, then its covering proof/finality observation to L1 withdrawal. No mock proof or synthetic state path was added. Parent supervision must still enforce the resource/deadline bounds and always stop node/prover descendants on failure. Full bridge execution remains unqualified by this source review.
