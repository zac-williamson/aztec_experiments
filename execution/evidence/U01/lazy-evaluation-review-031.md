# Lazy evaluation review 031

Read-only while genuine browser run 031 executes; no source edits, rebuild or test run. Initial inspection incorrectly used the retired shared bundle; the counts below were independently repeated against both current release paths before the next rebuild, with identical results. The retired artifact is not release evidence.

- Corrected current release inspection: `apps/dist/aztec_bundle.js` and `.build/sdk/aztec_bundle.js` are identical, 50,324,272 bytes, SHA-256 `09b8536aa12deec7616bd92dee6a7dbc150d19f7f53b3b722258120bbb24b94b`. The actual release contains **50 immediate private/hiding-kernel JSON object declarations**, **28 eager `abiToVKData` calls** in the reset/client VK tables, and **zero private/hiding-kernel lazy initializer factories**. These counts describe the currently generated bundle, not a hypothetical lazy build.
- `BundleArtifactProvider` statically references all real/simulated variants; its VK table converts fields into `Fr` objects and hex VK bytes into buffers at module evaluation.
- Pinned `LazyArtifactProvider` instead reaches each artifact through `client_artifacts_helper.ts` dynamic imports and invokes `abiToVKData` only when that VK is requested. ES module caching retains any artifact already evaluated; this is deferred evaluation, not eviction.
- The current IIFE build already demonstrates esbuild's deferred factory pattern for BB WASM imports: `Promise.resolve().then(() => (init_barretenberg_threads(), ...))`. Thus an IIFE can defer object construction without an ESM split, although all source text still ships and is parsed/compiled.
- Both production imports matter: `private-pxe.mjs` currently imports `/pxe/client/bundle` **and** subclasses `/bb-prover/client/bundle`. Changing only PXE would leave the subclass's eager artifact provider active.
- Recommended next candidate, if 031 needs it: switch both to the corresponding supported `/client/lazy` entries while preserving the existing streaming override, exact pinned artifacts, local verified CRS and two-thread policy. Inspect resulting bundle/metafile for disappearance of eager kernel tables and appearance of per-artifact factories before claiming any reduction.
- Treat the expected benefit as lower startup object/VK residency. It does not reduce download bytes automatically, prove a particular RSS saving, or change kernel/Chonk circuit complexity. A browser proof uses multiple variants and can eventually materialize much of the same data.
- No public `lowMemory` option exists in the reviewed pinned backend/prover APIs. `memory.maximum` constrains growth but is not a strategy for completing a proof with less working memory.
- BB's `barretenberg_wasm_main/index.ts` allocates permanent 8-MiB input and 8-MiB output scratch buffers per initialized heap. Inputs larger than 8 MiB receive a temporary allocation; normal completion frees it. Oversized output is copied out, then freed. This is additional to circuit/proof state and JS serialization buffers.
- Freeing allocations allows reuse inside the WASM allocator; it does not establish that grown shared linear memory shrinks or RSS immediately falls. The public API has no heap-compaction call here.
- `cbindCall` frees oversized buffers only after a successful WASM call; errors can bypass those frees. The new failed-instance quarantine is therefore appropriate. Destroying the shared singleton mid-operation would require separate lifecycle coordination.
- Existing streaming awaits reduce queued payload/decompression overlap, but original witness maps and BB's own accumulation/proof state remain. No source-only finding establishes that lazy evaluation will satisfy the unchanged 2-GiB bound.
