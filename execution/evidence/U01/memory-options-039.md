# Browser memory options 039 — 2026-09-17

Read-only pinned 5.2.0 source review while T02 runs. Reviewed 029/030/031/035 and current private-pxe/browser-chonk-stream. No builds, proving, measurements or source changes.

**One WasmWorker thread is a sound bounded experiment, not an established material memory fix.** Set the existing supported `threads` option to 1 at initial singleton creation, retaining WasmWorker, verified CRS, proof verification and the unchanged whole-test 2-GiB/540-second bounds. Check the same cached singleton policy consistently; do not switch an initialized singleton midway.

Precise source basis:

- `@aztec/bb.js/src/bb_backends/wasm.ts` creates one main worker in worker mode regardless of requested proving threads. `barretenberg_wasm/barretenberg_wasm_main/index.ts` creates `threads - 1` auxiliary workers. Changing 2 to 1 removes exactly one auxiliary worker/WASM instance and its worker runtime overhead; it does not move proof execution onto the UI thread.
- That auxiliary instance receives the **same WebAssembly.Memory** through `initThread(module, this.memory, ...)`; `barretenberg_wasm_thread/index.ts` instantiates with that imported memory. There is no second whole proof heap or duplicated SRS to eliminate. Main initialization allocates the two 8-MiB message buffers once; auxiliary initialization does not repeat it. Exact worker stack/runtime residency and C++ algorithm thread-dependent temporary allocations are not quantified by these JS sources.
- Main `env_hardware_concurrency` returns auxiliary-worker count plus one, so the one-thread option is actually communicated to native WASM algorithms. `barretenberg_wasm/index.ts` selects threaded/nonthreaded module from shared-memory availability, not requested thread count: in the existing isolated browser, requesting one thread still uses shared memory. Do not claim a smaller nonthreaded binary or half-size heap.
- No exposed memory-saving guarantee or low-memory algorithm option was found. One thread may slow completion; only a genuine bounded run can establish whether any saving is sufficient and deadline-compatible.

Remaining payload copies:

- `BarretenbergWasmAsyncBackend.call` passes the encoded Uint8Array to the Comlink worker proxy without an explicit transfer list. Structured-clone transport therefore remains a potential encoded-input copy, followed by cbindCall copying input into WASM memory. Current sequential awaits avoid multiple application payloads queued concurrently, but do not remove these single-call copies. The supported Barretenberg API exposes no per-call transfer option; changing transport would be an upstream/backend change, not a wrapper configuration fix. Detaching caller-owned buffers is not safe as an unreviewed workaround.
- Streaming helper keeps each current decompressed circuit bytecode lexically live through that step's accumulate call, although non-final bytecode is no longer needed after awaited load. Moving non-final decompression into a load-only helper scope is semantically plausible and could make it collectible sooner. It guarantees neither collection nor RSS reduction; the existing source does not measure that retained size. The final hiding bytecode must remain available for the actual VK computation. This is a secondary small lifetime candidate, not a demonstrated solution to intrinsic accumulation memory.
- Witness serialization still creates compressed then expanded temporary data; bypassing serialization requires reproducing the pinned witness binary format and is outside a supported configuration change. Original execution-step Maps remain caller-owned (035).

Recommendation: if another browser experiment is warranted, measure only the supported initial one-thread change first, with exact same transaction, artifacts, process accounting and stage markers. Do not combine speculative transport, witness ownership or proof-lifecycle changes. Source evidence alone cannot promise this completes below 2 GiB; no stronger supported memory-reduction option was established here.
