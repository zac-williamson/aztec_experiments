Preparation only, 2026-09-14. C01 remains under acceptance; this does not activate or complete C02. No application edits, tests, builds or proof runs. Read `tasks/C02.md`, REQ03, decisions and interface sections 4/7 against the current contract and maintained tests.

## Concrete starting defects

`billboard/billboard_contract/src/main.nr:377–440` proves the supplied child/grandchild exists, then checks its previous link. It does not explicitly constrain that note's contract, owner, slot, schema, deposit chain, immediate sequence or relation to the deposit's head sequence. It computes a link using the expected board/owner/chain but the **supplied note's** owner/slot for its inner hash; that recomputation is not an authorization check. Progress takes the candidate's sequence directly. There is no future-timestamp or child/grandchild chronology assertion. Supplied hints can be ignored when screening is unnecessary or the first child is too young. Flags are read for dummies too.

This is a source-confirmed missing-constraint finding, not a new reproduced exploit. P03 recorded the same distinction for B05. C01's private chain identifier, eight-field owned live deposit and one-time claim are necessary prerequisites but do not repair the screening boundary.

## Small implementation sequence

1. Add one constrained candidate-authentication helper actually called by `post` for both candidates. Its expected board/caller/slot/chain must come from the executing context and selected deposit, never caller arguments. Check schema 1, exact contract and owner, exact posts slot, exact nonzero deposit chain; run `assert_note_existed_by` at the actual anchor and validate the returned metadata as well. Keep standard typed note hashing, randomness/nonce and actual membership verification intact. Do not introduce a raw-witness decoder or pretend typed u64 fields expose the original packed witness.
2. Validate the live deposit's link/sequence consistency, including screenedSequence <= headSequence and matching head/screened links exactly when those sequences match. Require child sequence = screenedSequence+1, previousLink = screenedLink, sequence <= headSequence, and computed link = headLink **iff** its sequence equals headSequence. Apply the analogous immediate-successor and head conditions to the grandchild. Use checked additions. This prevents jumping across an unscreened real entry, duplicate candidates, old roots and arbitrary progress values.
3. Require no hints when there is no unscreened history. Require the immediate child whenever history remains. A mature non-head child needs its immediate successor even if that successor is too young. Authenticate any supplied second candidate even when the first cannot advance; never let it advance ahead of the first. Reject a supplied successor beyond the actual head. Require candidate anchorTimestamp <= current anchor and grandchild timestamp >= child timestamp; equal timestamps are valid. Do not invent a comparison with the previous screened timestamp: DepositNote does not store it. Authentic board issuance and link continuity provide that preceding transition's provenance.
4. Keep progress/penalty changes tied only to candidates actually advanced. Dummies must not read public flag state. Preserve one consumed deposit and exactly one replacement. Update helper comments to distinguish inclusion from authorization and keep all private chain metadata out of public arguments/events.

**Scope boundary to resolve before marking acceptance:** interface §7 ultimately requires real-post `postExists`, actual public inclusion time and flagDeadline, not the current `anchor_timestamp + censor_window` approximation. Current code still treats `post_id` as a u32 global counter, lacks that final public record, and `_post_public` receives the earlier private timestamp. C03 is explicitly assigned independent identities/public ordering, with C05 handling the final timing/economic boundaries. C02 can implement metadata, ancestry and immediate ordering now, but must explicitly hand off the historical-public-record maturity check with C03's new storage and C05's deadline tests. Neither C02's nominal “too young” tests nor the no-post C01 bridge proves that final censor-window guarantee. Do not silently label all of interface §7 satisfied.
