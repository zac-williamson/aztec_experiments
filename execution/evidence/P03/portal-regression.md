# P03 portal artifact/accounting regression lane

## Result and scope

The maintained local EVM suite passed **9 tests across 3 suites, 0 failures and 0 skips**. It applies identical desired accounting properties to direct compilation of the current Solidity source and to the actual generated deployment creation bytecode. A separately pinned historical artifact reproduces both known defects and is rejected by the same current-artifact identity guard.

This provides B02/P03-A03 regression evidence and a maintained seam for A01-A02/A04 and C06-A01/A04. It does not establish bridge authentication, L2 proof validity, network deployment compatibility, reentrancy safety or complete escrow invariants. The bridge inbox and outbox are deliberately permissive local accounting fixtures, and this limitation is stated in the test source. No third-party endpoint, real fund or user key was used.

## Files and behavior

- `billboard/portal/test/PortalArtifactRegression.t.sol`: shared accounting properties, source deployment control, actual generated-bytecode deployment, and historical bad-artifact controls. No string slicing of production source is used.
- `billboard/portal/test/fixtures/known-bad-portal.hex`: only the creation-bytecode literal from the historical diagnostic; never a production deployment input.
- `billboard/portal/test/fixtures/known-bad-portal.json`: historical provenance, fixture length and hashes, and defect descriptions.
- `billboard/portal/foundry.toml`: adds a `regression` profile with outputs/cache under `.build/portal-tests`, and read permissions limited to the fixture directory and two generated deployment bytecode files.

The source and generated-bytecode suites each verify:

1. A configured minimum of 2 ETH rejects 2 ETH minus 1 wei without changing individual/aggregate liabilities or retaining ETH, then accepts exactly 2 ETH.
2. Two synthetic depositors fund 2 and 3 ETH respectively. Their withdrawals refund each individual, preserve the other depositor's record, and reduce aggregate liabilities and escrow balance from 5 to 3 to 0 ETH.
3. A complete withdrawal followed by a 3 ETH redeposit records only the new 3 ETH liability.

Before generated-bytecode deployment, the test reads both actual `apps/src/billboard/portal_bytecode.txt` and `apps/src/billboard/deploy/portal_bytecode.txt`, verifies their byte equality, then verifies equality with the freshly compiled `BillboardPortal` creation code. It executes those read bytes using EVM CREATE with the configured constructor arguments.

Known-bad controls are intentionally labeled as observations of defects, not acceptable production behavior:

- The fixture ignores the configured 2 ETH minimum, exposes 0.001 ETH, and accepts a 1 ETH deposit.
- With 5 ETH of deposits, refunding 2 ETH clears the individual record and returns ETH but leaves aggregate liabilities at 5 ETH despite only 3 ETH escrow remaining.
- Passing the fixture into the exact identity guard used by the generated-artifact tests reverts with `Generated bytecode differs from compiled source`.

## Toolchain and commands

Executed from the repository root on macOS, using local pinned dependencies only:

```bash
forge --version
FOUNDRY_PROFILE=regression forge test --offline --root billboard/portal -vv > execution/evidence/P03/portal-regression.log 2>&1
git diff --check
```

Observed Foundry `1.4.1-v1.4.1`, commit `cf7746048646f2ecff48246dd61e265e49ab16f0`. The test compilation metadata reports solc `0.8.27+commit.40a35a09`, EVM `prague`, optimizer enabled with 200 runs and IPFS bytecode metadata. Portal dependency package `@aztec/l1-artifacts` reports `5.0.0`, matching the existing lock/pin. No dependency install or compiler download occurred.

The final test command exited 0. Raw results: [portal-regression.log](portal-regression.log). `git diff --check` exited 0.

Initial attempt without `--offline` compiled successfully but then the Foundry process crashed in macOS system proxy discovery (`system-configuration` / `OpenChainClient`, `Attempted to create a NULL object`). Preserved output: [portal-sandbox-attempt.log](portal-sandbox-attempt.log). Explicit offline execution avoids that optional lookup and passes all tests. This is an environment/tooling failure, not a portal failure; no missing tests from the crashed attempt are counted.

## Provenance and limitations

The known-bad bytes were extracted once from the historical diagnostic `review/portal-probes/src/PortalArtifactProbe.t.sol`, whose SHA-256 was `76e6f61692a55bd77ad5c19e84b5de59f6cc61a09e8a834103e65c4e21409b6a`. The repository-owned fixture contains 3202 bytes, raw bytecode SHA-256 `b990b437bf38a28a3f4606685d6d04cfb2e458773dbe7b4c60906c31ff253fcd`; the test checks that hash before executing historical accounting observations. Future runs need no sibling review directory.

All identities are synthetic EVM addresses funded by Foundry's local balance cheatcode and reset per test. Outbox consumption succeeds without proving a real Aztec message. The suite verifies portal accounting in the assumed authenticated-withdrawal branch only; C06 and end-to-end test gates still need real-message authentication/replay and full failure-path coverage. It is not an independent external audit.

Source/test/config were frozen before root's integration rebuild. Production Solidity was not edited in this lane. If any generated deployment bytes change during a later build, rerun this same command and reconcile these hashes before binding final acceptance.
