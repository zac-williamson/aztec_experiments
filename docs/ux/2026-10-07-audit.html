Message board UX audit

60 concrete findings across the entire application, with proposed fixes.

7 October 2026 · source snapshot 7ec9035 · proposal only

The main failure is structural: the interface exposes transaction machinery and asks people to manage it. A confirmed transaction does not establish an understandable, usable product.

What I checked

  • Chrome live: boards.html, feed.html, user.html (fresh entry and the user’s successful-post state), fee-juice.html, censor.html, deploy.html, Account menu.
  • Code: shared controls/styles/error mapping; all six templates/controllers; relevant account, funding, claim, post and withdrawal operations.
  • Read-only audit: no payments, posts, moderation, withdrawals, wallet prompts or application modifications. Account menu restored closed; temporary viewport override reset.
  • Not live-exercised in this audit: failure injection, withdrawal settlement, moderator/deployer transactions, fresh-device passkey recovery, screen reader, light theme and true mobile viewport. Those findings are labelled Code; mobile remains an explicit verification gap.

Proposed product model

Read the board → connect when ready to write → review the deposit and costs → approve the required wallet requests → the app finishes setup → write and read.

Onboarding ends at the board. Account contains session controls, funds, backup and Activity. Getting the deposit back is a separate guided operation. Waiting, proving and recovery are durable application states, not separate chores assigned to the user.

The remote-proving choice stays a single toggle, on by default when the board provides it, with a short visible privacy explanation. Changing it affects future operations; the active operation retains its original configuration.

Implementation order and acceptance gates

  1. State and recovery first. Typed user-facing outcomes; distinguish connected/ready/waiting/failed; automatic reconciliation; reachable Activity; safe retry and session switching. No text matching or UI timers controlling transaction correctness.
  2. Replace the wizard with the board. Shared reader/composer, persistent board identity, Account navigation, separate withdrawal task. A successful post leaves the person in a useful writing/reading state.
  3. Make funding understandable. Payment review, real balances, one onboarding action and honest progress. Expected bridge waits never become generic failures or requests for another deposit.
  4. Make writing and reading ordinary. Clear readiness, inline capacity validation, draft behavior, one success message, times, sharing and consistent feed updates.
  5. Finish withdrawal and account recovery. Guide screening and settlement, resume across sessions, show final receipt. No manual hash accounting in the normal path; distinguish passkey recovery from claim-secret recovery.
  6. Repair operator tools. Preserve selected board, message-based moderation, authority-transfer review and a deployment checklist that ends in a verified usable board.
  7. Apply one visual and accessibility system. Correct contrast and checkbox layout, readable text, consistent action hierarchy, keyboard/focus order and meaningful announcements.
  8. Qualify the experience on testnet. Use isolated real MetaMask with automated test-wallet approvals and realistic waits. Cover fresh and returning accounts, cancellation, low balances, bridge delay, prover outage, reload during work, long text/emoji, post, withdrawal and final completion. Inspect Chrome, both themes, narrow screens and keyboard use. Successful chain receipts are necessary but not sufficient.

Architecture: the UI consumes structured operation/account data and invokes explicit application APIs. Existing signing, journals and proof ownership remain behind those interfaces. UI components do not own transaction lifecycles, retry decisions or account mutation. No new framework is implied.

Deeper design decisions: reliable recovery of payment secrets on a fresh device and reduction of wallet approvals may require custody/protocol work. Do not promise those as copy-only fixes. Board labels need an explicit trusted metadata source. Actual settlement delays and required wallet authorization cannot be removed with presentation.

Catalogue

P1: confusing or unsafe core workflow, recovery, money, identity or privacy decision. P2: substantial clarity, presentation, navigation or accessibility problem. Every item is proposed; none is marked implemented by this audit.

Product structure

UX-01 · P1 — Posting is step 3 of a withdrawal wizard

Evidence: Chrome + code

A successful author sees “3 / 5” and a prominent “Proceed to Withdraw”. The product makes the main activity look incomplete.

Proposed fix: End onboarding when posting becomes available. Make the board and composer the home screen; put “Get deposit back” in Account.

apps/src/billboard/user/app.js:70; template.html:134

UX-02 · P1 — Infrastructure copy precedes the actual task

Evidence: Chrome + code

Fee reservations, local proving data, privacy caveats and a vague alpha warning consume the first screen before Connect.

Proposed fix: Lead with board identity, messages and one primary action. Show a short explicit testnet notice; put explanations at the decision they affect.

apps/src/billboard/user/template.html:10–19

Evidence: Chrome + code
